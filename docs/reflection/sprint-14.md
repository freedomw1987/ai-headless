## 🐛 Sprint 14 揭露並修正的真實問題

### 問題 1：event / todo spec 缺少 `requiresExtension`
- **揭露路徑**：disable-guard-api.spec.ts E2E 測試失敗（disable event 後 GET 仍 200）
- **根本原因**：Sprint 9 建立 spec 時只 blog 補了 `requiresExtension: "blog"`，event/todo 從未補
- **影響**：dynamic handler 的 `checkDisabled` 直接 return null → disable guard 完全沒生效
- **修**：手動驗證後補完 `extensions/event/event-spec.json` + `extensions/todo/todo-spec.json`
- **Sprint 教訓**：Sprint 9「每個 spec 都有 disable guard」是 **false claim**，要等 Sprint 14 dynamic handler 才真的驗證

### 問題 2：setExtensionEnabled 在 disable-guard-api 內有 race bug
- **揭露路徑**：同 E2E 測試失敗的副作用
- **根本原因**：`current.isEnabled` 是 closure 變數，while loop 內沒被重 fetch
- **修**：每次 while 開頭重新 fetch current 狀態

### 問題 3：Sprint 14 設計改變導致既有測試預期失效
- **disable error code** 從 `ExtensionDisabled` 常數改為描述性 string `"Extension \"blog\" is disabled"`
- **disable page guard** 從「redirect 到 /admin」改為「顯示 Extension 已停用訊息」
- **修**：更新測試期望 + 移除對 `extension` 欄位的檢查

### 問題 4：dynamic-handler comment 殘留舊 reference
- `lib/runtime/dynamic-handler.ts` 內還提到「generated by compiler」
- **修**：改為「由 runtime 動態組裝」

## 🔑 Sprint 14 關鍵教訓

### 教訓 1：用戶反思推翻 Sprint 規劃不是失誤
- Sprint 13 reflection 規劃 Sprint 14 為「修撤手寫誤區」（繼續 compiler 路線）
- 用戶 Sprint 13 完成後反思：「compiler 不是 silver bullet，是 bug 溫床」
- **教訓**：sprint reflection 應記錄「為什麼放棄原方向」的決策，避免未來重蹈覆轍
- **本次處理**：本 reflection 開頭明確標記「方向大轉彎」

### 教訓 2：手動 dev server 驗證揭露 typecheck 看不見的 bug
- Sprint 13 教訓：typecheck 過 ≠ compiler 真能用
- Sprint 14 同樣教訓：typecheck 過 ≠ runtime 真能用
- **這次揭露**：event/todo 缺 `requiresExtension`，disable guard 完全失效
- **解法**：每個 sprint 結束前強制跑「dev server + curl」手動驗證關鍵 flow

### 教訓 3：「Why not both」原則
- 用戶 80% / 20% 模型：JSON spec runtime 處理 80% 標準 CRUD，extension code 處理 20% 複雜邏輯
- 不互斥而是並存：workflow code、hook code、custom action 都可存在 extension 內
- **驗證點**：4 個 spec 的 `extensions/*/workflow/*.ts` 全部保留並繼續運作

### 教訓 4：API + UI URL 統一在 runtime layer
- 之前 Sprint 9-13：每個 spec 自訂 `/api/<spec>` + `/admin/<spec>`（sprint 10 後加 `apiBase` / `uiBase`）
- Sprint 14：統一 `/api/crud/<spec>` + `/admin/crud/<spec>` + query param 處理 id/event
- **好處**：manifest nav.path 完全一致，新增 spec 不用動 routing

### 教訓 5：Prisma model 手動維護的權衡
- Sprint 13 用 compiler 生成 Prisma schema（自動但易錯）
- Sprint 14 改為手動維護 `prisma/schema.prisma`
- **權衡**：失去自動生成，但程式碼變數名稱（`EventRegistration` vs `Registration`）更明確
- **現狀**：12 個 model 手動維護，目前仍可控制
